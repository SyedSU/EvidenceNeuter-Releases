# Protected release operations

This branch publishes nothing. All downloads remain disabled. Before public operation configure independently reviewed RSA3072+ public trust in Hub and distribution repository variable DISTRIBUTION_PUBLIC_KEY_PEM; configure an independently reviewed Authenticode SHA256 signer certificate pin in Hub. Keep signing private keys in offline/HSM custody, never Git or workflow logs.

Create `distribution-release` environment with required human reviewers, no self approval, main-only deployment and least-scope DISTRIBUTION_WRITE_TOKEN. The manual workflow verifies an explicit immutable source commit and signed reviewed JSON before the protected job. It uploads JSON to an EXISTING release only and never creates releases or overwrites assets. Configure the environment before enabling workflow use: YAML cannot enforce GitHub environment settings. No PR job receives signing/publishing secrets. Package building and signing occur separately; signing hosts must not execute upstream build scripts.

Generate deterministic component ZIPs using `python tools/distribution.py package <directory> --output <artifact.zip>`. Inspect license notices and all file hashes. Validate Genesis manifest with schema1 and minimumHubVersion; require Genesis0.4.0 saveSchema4. Runtime and model have independent actual source/version provenance in catalog. Use full40hex compatible source locks for Hub/Genesis, then `check_lock` before producing candidates. Never replace a missing source provenance with a guessed SHA.

Review/sign exact payload bytes using offline `sign` CLI and an externally supplied PKCS8 private key. Verify with `verify --key <reviewed-public.pem> --kind catalog|manifest|hub`. New metadata sequence must exceed highest prior accepted signed metadata; current repository has zero releases. Signer expiry must be at most30days and release sequence tracked in protected operator records. Package URL hashes do not establish trust by themselves.

Renewal: recover the last VERIFIED signed payload, keep version/source/package facts unchanged, increment sequence beyond all accepted sequences, set fresh expiry, review and sign. Publish a new immutable metadata asset first; separately reviewed locator switching is required. Existing genesis-stable locator remains Genesis schema1; never put a catalog at this locator. Manual upload refuses clobber; metadata refresh must use distinct asset names. Offline installed games retain expiry exception, online downloads reject expired metadata.

Key compromise/recovery: immediately block catalog downloads, stop publishing, audit approved immutable packages and signing custody. Schema1 cannot revoke/rotate remotely. Produce a new independently reviewed Hub installer pinning a replacement root and Authenticode publisher, distribute through a separately authenticated route, re-sign audited metadata and record new trust epoch. Never accept a replacement public key downloaded beside metadata. Keep old installed offline play policy explicit.

Public gate prerequisites: genuine Windows installer/game acceptance, correct saveSchema4 incompatibility handling, independently signed installers with valid WinVerifyTrust and known fingerprint, real published signed manifests/packages, approved licenses, screenshots and component provenance. Model/runtime weights and executables stay outside Git. Website and Hub only enable downloads after authenticated catalog and every gate flag; local boolean flags never supply authentication.

## Reviewed activation bundle

For a public catalog candidate supply `hub_envelope_path`, `genesis_envelope_path`, `hub_manifest_url`, and `genesis_manifest_url` to the protected manual workflow. Referenced JSON envelopes are independently authenticated before comparing installer URL/bytes/hash, product versions/source/platform/channel, Genesis save epoch and minimum Hub compatibility. Configure separately reviewed public key variables HUB_MANIFEST_PUBLIC_KEY_PEM and GENESIS_MANIFEST_PUBLIC_KEY_PEM and independently reviewed HUB_PUBLISHER_SHA256. Schema1 may share an explicitly reviewed RSA root; no payload-supplied key is accepted. The workflow has no Windows signer acceptance evidence; genuine WinVerifyTrust/publisher acceptance remains external gate evidence.

Publish approved referenced metadata/assets first; only then activate catalog and the byte-preserving same-origin `hub-release.json` website mirror as one reviewed deployment bundle. Do not pretty-print/re-encode signed envelope payloads, replace trust from metadata, or deploy catalog and mirror from unrelated releases. Static CSP remains unchanged. Candidate validation refuses absent envelopes or mismatched catalog installer facts even when every signed catalog gate flag is true. Nothing in this branch invokes publishing or website production deployment.

HUB_MANIFEST_PUBLIC_KEY_PEM and GENESIS_MANIFEST_PUBLIC_KEY_PEM are mandatory for public activation even when deliberately sharing the reviewed catalog RSA root; identical PEM values must be explicitly configured in each role. Tool APIs reject missing hub_key/genesis_key rather than infer a parent trust role.
